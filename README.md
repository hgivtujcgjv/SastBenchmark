# SastBenchmark — Go (только stdlib)

Набор тест-кейсов для проверки полноты и точности статических анализаторов.

> **Внимание.** Этот код содержит намеренные уязвимости и предназначен только для тестирования
> статических анализаторов в изолированной среде. Не разворачивайте его и не используйте фрагменты
> в рабочих проектах.

## Состав

- **Кейсов:** 50
- **Идентификаторы:** BenchmarkTest05001 – BenchmarkTest05050
- **Категорий:** 10

| Категория | CWE |
|---|---|
| `cmdi` | CWE-78 |
| `jwt` | CWE-347 |
| `pathtraver` | CWE-22 |
| `racecond` | CWE-362 |
| `sqli` | CWE-89 |
| `ssrf` | CWE-918 |
| `tlsverify` | CWE-295 |
| `weakrand` | CWE-338 |
| `xss` | CWE-79 |
| `zipslip` | CWE-22 |

Каждая категория содержит и уязвимые кейсы, и безопасные контроли. Безопасные написаны так,
что содержат настоящую митигацию — срабатывание на них означает, что анализатор не распознаёт
конкретный санитайзер. Уязвимые кейсы внутри категории — это **один и тот же дефект в разных
синтаксических формах**: правило, привязанное к одной форме, найдёт часть и пропустит остальные.

Разметка (какой кейс уязвим, какой безопасен) намеренно **не включена в эту ветку** —
прогон предполагается слепым. Ключи ответов лежат в ветке [`results`](../../tree/results).

## Структура

`testcode/` — кейсы, `go.mod` (модуль без внешних зависимостей)

## Сборка

```bash
go build ./... && go vet ./...
```

Большинству SAST достаточно исходников — собирать не обязательно.

## Как считать результат

1. Прогнать анализатор по набору.
2. Сопоставить сработки с кейсами по имени файла (`BenchmarkTestNNNNN`).
3. Сверить с ключом из ветки `results`: сработка ожидаемого класса на уязвимом кейсе — TP,
   её отсутствие — FN; сработка на безопасном кейсе — FP, отсутствие — TN.
4. Сработки других классов на том же файле фиксировать отдельно как побочные —
   в TP/FP по категории они не идут.

Зачёт стоит делать семантический, а не по буквальному совпадению названий: разные анализаторы
называют один класс по-разному. Подробнее — в ветке `results`.
